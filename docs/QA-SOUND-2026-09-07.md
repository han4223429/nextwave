## 반영한 동작

- Web Audio로 물방울 클릭음, 여러 방울이 퍼지는 잔물결, 짧은 물소리, 맑은 두 음의 화음을 합성한다. 외부 음원 요청과 배경 반복 재생은 없다.
- 수면 터치·키보드 물결 생성은 `ripple`, 수면 드래그 완료·모드 변경·사용자의 섹션 스크롤은 `wave`, 프로젝트 선택은 `chime`으로 반응한다. 게임은 발사·명중·대시를 구분한다.
- 기본 설정은 켜짐이지만 첫 사용자 조작 전 AudioContext나 소스를 만들지 않는다. 홈·포털의 SOUND 버튼과 저장된 `nw:sound` 값이 공통 설정이다.
- 음소거와 탭 숨김은 활성·예약 소스를 정리하고 context를 suspend한다. 늦게 완료된 resume이 음소거를 되돌리지 못하게 하고, 탭 복귀만으로 소리를 다시 시작하지 않는다.
- master gain 0.16, 최대 동시 효과 4개, 종류별 반복 간격, 짧은 envelope와 필터·compressor로 재생을 제한한다. 지원하지 않는 브라우저는 소리 버튼을 비활성화하고 나머지 기능을 유지한다.

## 확인 범위

사이트 코드는 [86fc14d](https://github.com/han4223429/nextwave/commit/86fc14d)에 업로드했습니다. 자동 수집 workflow는 Git 인증의 `workflow` scope 부족 때문에 분리했으며, GitHub 앱을 통한 등록도 자동 승인 검토가 예약된 `contents:write`·`pages:write` 권한의 명시적 승인 부족으로 거절했습니다. 검증된 로컬 파일을 유지하고 정확한 등록 승인을 요청했습니다. 따라서 위 workflow 검사는 로컬 준비 상태의 검사이며, 예약 작업의 원격 실행 성공을 뜻하지 않습니다.

Chrome 검사는 Web Audio의 실제 실행 상태와 소스/효과 진단값을 확인한다. 자동화 도구가 출력 음성을 들려주지는 않으므로 주관적인 청감 검증 완료로 표현하지 않는다. 자연 수면·RESCUE 모델의 기존 화면 검사는 [물결 QA](QA-WATER-2026-09-06.md)에 기록했다.

Google 기존 로그인은 계정 선택 후 일반 401을 재현했다. 준비한 공식 Google Identity 경로의 인증 완료는 OAuth 원본 추가·저장 승인이 필요해 미검증 상태다. 정확한 관찰과 자동 승인 검토의 차단 이유는 [인증 진단](QA-AUTH-2026-09-06.md)을 따른다. 운영 Firestore 규칙 배포와 실제 계정 권한 변경은 이번 Git 업로드에 포함되지 않는다.

## 브라우저 검증

Chrome의 실제 `localhost:8000` 홈페이지와 공개 포털에서 확인했다. 최종 재검사 주소는 `http://localhost:8000/?v=water-sound-5`이며, DOM에 공개한 AudioContext 상태·master gain·효과 종류·횟수·활성 소스 진단값을 사용했다. 계정 로그인이나 승인 대기 중인 OAuth 설정 저장은 수행하지 않았다.

| 확인 항목 | 실제 관찰 |
| --- | --- |
| 조작 전 | SOUND ON이어도 context `uninitialized`, 효과 0회, 활성 소스 0개. 자동 재생 없음. |
| 첫 조작 | 첫 마우스 조작 후 `running`, master gain 약 0.16. 최종 코드의 첫 키보드 Enter도 `ripple` 1회를 정상 재생 요청했다. |
| 효과 구분 | 파문 생성 `ripple`, WAVE 모드 `wave`, 일반 링크 `tap`, 프로젝트 탭 `chime`으로 서로 다른 진단값과 횟수 증가를 확인했다. |
| 모바일 직접 조작 | 390px에서 실제 수면 드래그 완료가 `wave`, 수면 직접 클릭이 `ripple`로 각각 한 번씩 반응했다. WAVE 버튼도 계속 클릭 가능하고 선택 상태가 표시됐다. |
| 키보드 음소거 | Enter로 음소거 후 `suspended`, master gain 0, 활성 소스 0개. 음소거 중 수면 버튼을 눌러도 효과 횟수가 증가하지 않았다. |
| 설정 유지 | 홈에서 음소거한 뒤 실제 포털 이동·새로고침에서도 SOUND OFF와 조작 전 무재생 상태가 유지됐다. 포털에서 키보드로 켜면 `running`과 `chime`이 확인됐고 두 포털 소리 버튼 상태도 일치했다. |
| 반응형 | 홈과 공개 포털을 390px·320px에서 확인했다. 가로 넘침이 없고 로고·소리 버튼·메뉴/클럽 홈이 잘리지 않았다. 포털 헤더 높이는 74px였다. |

검사 중 모바일 `.hero-bottom`의 빈 350px 패딩 영역이 포인터를 받아 수면 드래그를 가리는 결함을 발견했다. 빈 컨테이너는 `pointer-events: none`, 실제 링크·버튼·모드 컨트롤은 `auto`로 수정한 뒤 직접 드래그·클릭·컨트롤 버튼을 재검사하여 통과했다. 첫 키보드 unlock 경쟁과 음소거 gain 진단값도 최종 수정 후 위 표의 상태로 재확인했다.

CUA가 만든 새 탭에서도 이전 문서의 `document.hidden`이 `false`로 유지되어 실제 숨김 전환을 재현하지는 못했다. 숨김 시 정리는 위 자동 검사의 근거만 사용한다. hover에 연결된 재생 핸들러가 없다는 소스 확인과 조작 전 효과 0회 관찰을 했으며, 실제 출력 음질이나 청감은 검증하지 않았다. 화면 캡처는 CUA 도구 결과로 확인했으며 별도 로컬 이미지 파일로 저장하지 않았다.
