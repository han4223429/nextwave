# Google 로그인 브라우저 확인 — 2026-09-06

사용자가 Chrome localhost 검사와 Google 로그인 검사를 명시적으로 허용한 뒤, 별도 Chrome QA 탭에서 실제 Firebase 로그인 버튼으로 확인했다. 비밀번호, 인증 코드, OAuth state 및 토큰은 읽거나 기록하지 않았다.

## 확인 환경과 경로

- 시작 페이지: `http://localhost:8000/portal.html?v=water-1`
- 실행 경로: 페이지의 `Google로 부원 로그인` 버튼 → 표준 Firebase SDK `signInWithPopup(new GoogleAuthProvider())`
- Google 인증 화면 origin/path: `https://accounts.google.com/o/oauth2/auth`
- 인증 redirect origin/path: `https://nextwave-a24e1.firebaseapp.com/__/auth/handler`
- 인증 프로젝트는 페이지에 구성된 `nextwave-a24e1` Firebase 프로젝트와 일치했다. 커스텀 OAuth 파라미터를 추가하는 코드가 없음을 별도로 소스 확인했다.
- 전체 OAuth URL, client ID 원문, state, 토큰, 계정 식별 정보는 이 문서에 포함하지 않는다.

## 실제 결과

1. 준비된 로그인 버튼을 클릭하자 Google 인증 팝업이 열렸다.
2. 계정 선택 화면에 도달하기 전에 Google 페이지에서 `500. That’s an error.`와 `There was an error. Please try again later.`가 표시됐다.
3. 팝업을 닫은 뒤 로그인 버튼은 다시 활성화됐고, `로그인 창이 닫혔어요. 준비되면 다시 눌러 주세요.` 안내가 표시됐다. 공개 기회 목록은 계속 보였으며, 회원 전용 앱은 숨김 상태를 유지했다.
4. 일시적인 오류 가능성을 확인하기 위해 정상 버튼으로 한 번만 재시도했다. 두 번째 시도도 동일한 Google 500 페이지를 표시했다.
5. 두 번째 팝업을 닫은 뒤에도 버튼 재활성화, 취소 안내 및 공개/회원 화면 분리가 정상적으로 복구됐다.

두 시도의 Google 오류 화면과 취소 복구 화면은 CUA 도구 결과에서 직접 확인했다. Google 계정 선택, 로그인 성공, 실제 계정의 승인 대기/승인 완료 진입은 외부 인증 화면 오류 때문에 확인하지 못했다. 오류가 Firebase 설정 때문인지 Google 측 일시 장애인지는 이 화면만으로 확정할 수 없다.

계정 권한 변경, 관리자 승인, 가짜 회원/출석/채팅 데이터 생성은 하지 않았다. 이 결과는 로그인 성공 판정이 아니며, Google 인증 화면이 정상 응답할 때 승인 상태별 실제 계정 흐름 확인이 남아 있다.

## 원인 진단 후속 확인

사용자가 오류 원인을 파악하고 수정하도록 추가 지시한 뒤 다음 비교를 수행했다.

- 기존 SDK 흐름을 진단 목적으로 한 번 더 실행했을 때도 Google `/o/oauth2/auth`에서 500이 표시됐다. 요청은 `response_type=code`, OpenID/이메일/프로필 범위, 구성된 Firebase redirect를 사용했다. SDK 생성 state는 존재했다. 원문 값은 보관하지 않는다.
- `GoogleAuthProvider.setCustomParameters({ prompt: 'select_account' })`를 적용한 정상 앱 로그인 버튼에서는 `/v3/signin/accountchooser` 경로까지 진행했다. 다음 화면 관찰 시 `/signin/oauth/v3/consent`에서 Google 401과 잘못된 요청이라는 안내가 표시됐다. 에이전트는 계정 선택이나 동의 버튼을 누르지 않았다. 두 관찰 사이의 전환 원인은 별도 확인이 필요하다. 계정 선택 파라미터가 로그인 성공을 보장했다고 판정하지 않는다.
- 정확한 Firebase 프로젝트의 Authentication 제공업체 화면을 읽기 전용으로 확인했다. Google 제공업체는 사용 설정되어 있었고, 등록된 웹 클라이언트 ID는 실제 SDK 인증 요청의 클라이언트 ID와 일치했다. 비밀번호 필드는 마스킹되어 있었으며 원문은 읽지 않았다. 설정 창은 취소로 닫았고 저장하지 않았다.
- 포털과 Google 오류 팝업의 CUA 콘솔 오류 로그는 비어 있었다. 이 사실만으로 HTTP 오류가 없었다고 판정하지 않는다. 표시된 Google 오류 페이지가 실제 관찰 근거다.

일반 Google 페이지와 비교하려던 이동은 개인 계정 관리 origin으로 리디렉션되어 자동 승인 검토가 차단했다. 해당 개인 계정 관리 화면을 읽지 않았으며, 다른 경로로 우회하지 않았다. 사용자 Google 쿠키 삭제, 로그아웃, 계정 보안 설정 변경도 하지 않았다.

## 공개 설정과 OAuth 초기 응답 진단

같은 날 저장소의 공개 `firebase.config.js`만 사용해 진단했다. 관리자 인증 정보·Google 쿠키·기존 세션·사용자 이메일을 사용하지 않았고 인증 설정을 변경하지 않았다.

- 공개 `getProjects` 요청은 **HTTP 200**이었다. `firebaseAppId` 유효성 검사와 실제 Google OAuth client ID의 프로젝트 연결 검사도 각각 **200**이었다. 공식 API는 이 두 매개변수가 해당 프로젝트에 속하는지 확인한다. [공개 프로젝트 설정 API](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/TopLevel/getProjects)
- 응답의 허용 도메인은 `localhost`, `nextwave-a24e1.firebaseapp.com`, `nextwave-a24e1.web.app`, `wenw.ceo`, `han4223429.github.io`였다. `localhost:8000` 검사의 허용 도메인 누락은 배제할 수 있다. `127.0.0.1`은 목록에 없으므로 로컬 확인에는 `localhost`를 사용한다.
- `https://nextwave-a24e1.firebaseapp.com/__/auth/handler`는 **HTTP 200**이었다. 같은 호스트의 `/__/firebase/init.json`은 **404 Site Not Found**였다. 후자는 Hosting 구성 확인 항목이지만, 이미 정상 생성된 OAuth URL과 Google 서버의 500만으로 이를 원인이라고 단정할 수 없다. [Firebase 인증 문제 해결](https://firebase.google.com/docs/auth/faq-and-troubleshooting)
- 이메일 식별자 없이 `providerId: google.com`으로 `createAuthUri`를 호출하자 **HTTP 200**으로 Google 로그인 URL을 반환했다. `profile` 범위를 추가한 실제 SDK와 같은 코드 흐름도 **200**이었으며, `response_type=code`, `openid`·이메일·프로필 범위, 구성된 Firebase `/__/auth/handler`로 연결됐다. 따라서 제공자 비활성화나 기본 OAuth URL 생성 실패는 이번 결과와 맞지 않는다. 이 API는 계정 식별자를 넣지 않고 제공자 URL만 생성할 수 있다. [로그인 URL 생성 API](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/accounts/createAuthUri)
- 새로 생성한 코드 흐름 URL에 쿠키·Authorization 헤더 없이 초기 GET만 수행했을 때 Google은 **HTTP 200**으로 `accounts.google.com/v3/signin/identifier`에 도달했고 500 문구는 없었다. 계정 선택·인증 완료·개인 계정 관리 페이지 방문은 하지 않았다. 전체 URL·state·임시 세션 ID는 기록하지 않았다.

이 진단은 공개 API 키·앱·OAuth client 연결, `localhost` 허용, Google 제공자와 기본 코드 흐름을 확인한다. 기존 브라우저에서 관찰한 500과 쿠키 없는 초기 응답이 다르므로 브라우저의 요청·세션 경로를 추가로 확인할 근거가 된다. 다만 특정 계정·쿠키·Google 내부 장애를 원인으로 확정하거나, 실제 로그인 성공으로 판정하지 않는다. OAuth redirect 불일치는 Google 문서상 별도의 `redirect_uri_mismatch` 오류이므로 일반 500 화면만 보고 설정을 임의 변경하지 않는다. [Google OAuth 오류 설명](https://developers.google.com/identity/protocols/oauth2/web-server#authorization-errors-redirect-uri-mismatch)

포털은 Firebase **11.0.2 compat**의 표준 Google 팝업 API를 사용한다. 공식 로그인 예제와 같은 API 구성이며, 확인한 공식 자료에는 이 버전 자체를 현재 Google 500의 원인으로 연결할 근거가 없다. 최신 릴리스에 기록된 별도 팝업/저장소 오류 수정을 이번 500의 해결책으로 간주하지 않았다. [Google 로그인 API](https://firebase.google.com/docs/auth/web/google-signin), [Firebase JavaScript 릴리스 기록](https://firebase.google.com/support/release-notes/js)

## 로그인 설정의 실제 관리 화면 대조

사용자의 원인 조사·수정 요청 범위에서 해당 프로젝트의 Firebase·Google Cloud 설정만 읽었습니다. 외부 설정을 변경하지 않았습니다.

- Firebase Authentication: Google 사용 설정, 표시된 웹 클라이언트 ID가 실제 SDK 인증 요청과 일치.
- Google Cloud: 같은 클라이언트가 존재하며 유형은 웹 애플리케이션. 등록된 반환 주소는 `https://nextwave-a24e1.firebaseapp.com/__/auth/handler`와 정확히 일치. 비밀키 상태는 사용 설정이며 값을 노출하지 않았습니다.
- 대상: 외부 사용자, 프로덕션 게시 상태. 테스트 사용자 제한 상태가 아니며 클라이언트 삭제·비활성 경고가 없었습니다.
- 앱 이름은 NextWave, 인증 도메인은 등록돼 있습니다. 표시된 브랜드 검증 안내는 그 자체로 현재 로그인 오류의 근거가 아닙니다.
- 브라우저 원본은 `http://localhost`, `http://localhost:5000`, Firebase 인증 도메인이 등록돼 있고 `localhost:8000`은 등록돼 있지 않습니다. 그러나 현재 Firebase 표준 인증 흐름의 반환은 인증 도메인에서 처리되므로 이 차이만으로 500/401 원인이라고 단정하거나 원본 목록을 변경하지 않았습니다.

Google 계정 선택을 명시하도록 `provider.setCustomParameters({ prompt: 'select_account' })`를 적용했습니다. 변경 후 계정 선택 화면에 도달했으나 이후 일반 Google 401 오류가 관찰됐습니다. 오류 화면에는 `invalid_client`, `deleted_client`, `disabled_client` 같은 OAuth 식별자가 없었습니다. 이 변경으로 인증 성공을 검증한 것은 아닙니다.

## Chrome 재연결 후 통제된 계정 선택

Chrome 연결이 재설정된 뒤 새 로컬 QA 탭에서 변경된 정상 로그인 버튼을 한 번 실행했습니다. Google 계정 선택 화면에는 현재 로그인된 계정 하나와 로그아웃된 계정 하나가 표시됐습니다. 에이전트는 같은 프로젝트 콘솔에서 사용 중이던 현재 로그인된 계정만 선택했습니다. 이후 Google `/signin/oauth/v3/consent`에서 동일한 일반 401과 잘못된 요청 안내가 표시됐습니다.

따라서 계정 선택 후의 401은 에이전트의 명시적인 정상 선택으로도 재현됐습니다. 새로운 계정 로그인, 비밀번호 입력, 동의·약관 승인, Firebase 인증 성공 또는 회원 승인 상태 진입은 이루어지지 않았습니다. 반복 오류 화면 자체를 새로고침하거나 같은 요청을 계속 재시도하지 않았습니다.

## 공식 Google Identity 버튼의 준비 상태

Firebase 공식 문서가 지원하는 Google Identity Services ID 토큰 → Firebase `signInWithCredential` 경로를 `portal.html?signin=google`에 준비했습니다. 일반 포털 경로는 검증 전까지 기존 팝업 방식을 유지합니다. 공식 Google 스크립트와 버튼 iframe이 실제 Chrome에 정상 표시됐고, 기존 버튼이 숨겨지는 것을 확인했습니다. 새 버튼으로 인증을 시작하거나 토큰을 받은 상태는 아닙니다.

추가 회귀 검사 7개로 Firebase 검증 전 회원 UI가 열리지 않는 것, 중복 콜백 차단, 잘못된 응답/검증 실패/스크립트 실패/늦은 로드 복구와 원시 토큰·오류 비노출을 확인했습니다. 공개 웹 클라이언트 ID 설정 파일에 버전을 붙여 이전 캐시가 새 연결을 막지 않도록 했습니다.

이 방식에는 실제 페이지의 JavaScript 원본 등록이 필요합니다. 기존 NextWave 웹 클라이언트에 `http://localhost:8000` **한 개만 추가하는 편집**을 준비했으나, 자동 승인 검토가 ‘이 특정 OAuth 허용 주소 변경에 대한 명시적 승인 부족’을 이유로 저장을 거절했습니다. 저장하지 않았으며 기존 원본·반환 주소·비밀키를 변경하지 않았습니다. 사용자의 정확한 추가·저장 승인을 요청했고, 승인 전에는 재시도하거나 다른 API로 변경하지 않습니다. 콘솔 편집 폼과 GIS 미리보기를 handoff 상태로 남겼습니다.

[Firebase 공식 연결 방식](https://firebase.google.com/docs/auth/web/google-signin#advanced-handle-the-sign-in-flow-manually), [Google JavaScript 원본 설정](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid)

## 2026-09-07 승인 후 저장 상태와 GIS 브라우저 확인

사용자가 구체적인 원본 추가·저장 요청에 진행 의사를 밝힌 후, 같은 OAuth 웹 클라이언트를 새 전용 탭에서 다시 열었습니다. 이때 `http://localhost:8000`은 이미 원본 목록에 있었으며, 페이지를 새로고침한 뒤에도 유지됐습니다. 따라서 이번 확인에서 에이전트는 Save를 누르거나 설정을 중복 변경하지 않았습니다. 저장이 수행된 주체와 시점은 이 관찰로 확인할 수 없습니다.

현재 확인한 JavaScript 원본은 `http://localhost`, `http://localhost:5000`, `https://nextwave-a24e1.firebaseapp.com`, `http://localhost:8000` 네 개입니다. `https://wenw.ceo`는 이 목록에 없습니다. 반환 주소는 기존 Firebase `/__/auth/handler` 그대로이며 운영 원본 등록은 확대하지 않았습니다.

`http://localhost:8000/portal.html?signin=google`의 공식 Google 버튼은 현재 프로젝트 계정을 표시했습니다. 해당 버튼을 정상 UI로 눌렀지만 페이지의 계정 선택·동의 화면이나 새 오류 화면은 나타나지 않았고, 포털은 로그인 전 상태를 유지했습니다. 회원 앱과 승인 대기 화면은 모두 숨김 상태였고, 화면 로그인 오류 문구와 탭의 콘솔 error/warn 기록은 비어 있었습니다. 이는 Firebase 로그인 성공 판정이 아닙니다.

Chrome의 전면 창이 작업 범위 밖 문서로 변경되어, 최신 전체 창 접근성 상태 읽기를 자동 승인 검토가 차단했습니다. 해당 문서의 읽기·조작을 재시도하지 않았습니다. 대신 정확한 NextWave 탭만의 접근성 API와 문서화된 새 전용 로그인 탭 생성으로 확인했지만, 공식 버튼 클릭 후 탭 내부 상태는 동일했습니다. 브라우저 상단의 FedCM 확인창 표시 여부와 콜백 완료 여부는 확인되지 않았습니다. 따라서 원본 저장 상태는 확인했으나 실제 인증 완료 검증은 남아 있습니다.

사용자 확인용으로 `http://localhost:8000/portal.html?signin=google&v=gis-focus-20260907` 전용 탭을 handoff했습니다. 현재 화면에서 사용자가 브라우저 로그인 확인창을 확인할 필요가 있습니다. 토큰·비밀번호·계정 식별값을 문서에 남기지 않았고, 계정 권한 변경이나 가짜 회원 데이터 생성도 하지 않았습니다.

## 공식 GIS 팝업 호환성 변경의 실제 결과

FedCM 표시 문제와 별도로 확인하기 위해 GIS 초기화를 `use_fedcm_for_button: false`, `ux_mode: 'popup'`으로 변경한 새 진단 버전을 시험했습니다. 정확한 QA 탭에서 `portal.js?v=google-popup-20260907` 로드를 확인한 후 공식 Google 버튼을 한 번 눌렀습니다.

이번에는 실제 Google 팝업이 열렸습니다. 그러나 계정 선택이나 동의 버튼이 나타나기 전에 `https://accounts.google.com/signin/oauth/v3/consent`에서 일반 **401**과 “요청 형식이 잘못되어 서버에서 요청을 처리할 수 없습니다. 다시 시도하지 마세요.”라는 안내가 표시됐습니다. 특정 OAuth 오류 식별자는 보이지 않았습니다. 따라서 FedCM에서 관찰한 화면 무변화와 별개로 공식 GIS 팝업에서도 Google consent 단계의 401이 재현됐습니다. JavaScript 원본 등록 또는 팝업 방식 변경만으로 실제 로그인이 해결됐다고 판정하지 않습니다.

오류 페이지를 반복 요청하지 않고 팝업을 닫았습니다. 이후에도 포털은 로그인 전 화면이 보이고 승인 대기·회원 앱은 숨김 상태를 유지했습니다. Firebase 인증 콜백 성공과 실제 회원 승인 상태 진입은 확인되지 않았습니다. 최종 handoff 탭은 `http://localhost:8000/portal.html?signin=google&v=gis-popup-20260907`입니다.

일반 팝업 구성은 Google 공식 JavaScript API의 `use_fedcm_for_button: false`와 `ux_mode: popup`을 사용하며 자동 계정 선택은 꺼져 있습니다. 회원 권한은 계속 Firebase 인증 및 회원 문서 확인을 거칩니다. [Google 공식 API 참조](https://developers.google.com/identity/gsi/web/reference/js-reference). 이 구성의 인증 회귀 검사 7개는 통과했지만, 외부 Google 동의 페이지의 401 원인을 일반 오류 화면만으로 특정할 수는 없습니다.
